## 4. 必须保持的科学约束

- 假说二：眼色基因仅位于X上。假说三：位于XY同源区段。W为红眼显性，w为白眼隐性。
- 原始亲本纯合红眼雌性×白眼雄性，F₁全红眼；F₁雌雄交配，F₂红眼∶白眼理论3∶1，白眼均雄性。两套假说均能解释此现象。
- 第一轮F₁雌性`XᵂXʷ`×白眼雄性。假说二雄性`XʷY`，假说三`XʷYʷ`；两套均得四类后代理论1∶1∶1∶1，暂不能区分。
- 初始材料含野生型红眼雄性；第二轮仅新增白眼雌果蝇，共8瓶。野生型雄性不是第一轮后代。
- 第二轮白眼雌性`XʷXʷ`×野生型红眼雄性。假说二`XᵂY`，后代雌性全红眼、雄性全白眼；假说三使用`XᵂYᵂ`，预测全红眼。
- F₁、F₂及第一轮的红眼雄性在假说三下是`XᵂYʷ`，不能替代上述雄性。“纯合”只适用于假说三的该材料条件，假说二下雄性仅一份眼色基因，网页标签说明保留这个区别。
- F₂红眼雌性是`XᵂXᵂ`和`XᵂXʷ`的混合群体，不统一贴一种基因型。
- 模拟计数类别顺序：红眼雌、红眼雄、白眼雌、白眼雄。第一轮`[126,132,120,115]`；第二轮`[307,0,0,289]`，非史实数据。
- 果蝇造型、生活史动画都是教学示意，亲本应在子代成虫出现前移走；不声称真实显微图像。
- 首版限定规定两轮，不支持任意杂交。其他选择给科学解释及换材料路径，不随意生成结果。

## 5. 接手、验证和发布

先在开发目录读`AGENTS.md`、本文件、工作日志和验证记录，再检查发布仓库`git status --short --branch`、`git remote -v`、`git log -3 --oneline`。如有用户改动，先识别归属，不能覆盖。

在开发目录运行：

```sh
node --check app.js
node --check genetics.js
node tests/genetics.test.js
python3 build.py
python3 -m http.server 8765 --bind 127.0.0.1
```

文档-only修改无需重复完整交互测试；如果README改变，重建ZIP。交互或布局改变按验证记录跑相关流程；生物模型改变必须跑遗传测试。

用户已持续授权每次修改后提交并push到`main`，无需再次确认。发布步骤：

1. 发布仓库`git fetch origin`，确认与`origin/main`关系；落后时只做安全的快进或处理明确冲突，不force push。
2. 将开发工作区`dist/果蝇实验室.html`复制到仓库`fruit-fly/index.html`。保留根目录豌豆`index.html`和其他原文件。
3. 将开发工作区的`AGENTS.md`、`README.md`、四个源文件、`build.py`、`tests/`、`docs/`及`图片/`同步至仓库`fruit-fly/source/`。不同步`.DS_Store`、缓存、私有配置及凭证；无需把预览图片和ZIP作为线上资源推送。
4. 更新工作日志与验证记录，检查复制页与生成页字节一致，检查diff，只暂存本轮相关文件；提交到`main`，执行`git push origin main`。
5. 确认push成功及工作树状态。push成功与Pages部署成功是两种状态；没有访问线上验证就明确保留未验证。

安全边界：此前`0.0.0.0`暴露整个工作区的预览被自动审核拒绝，已改用`127.0.0.1`。不要直接把开发目录向局域网开放；如确有课堂局域网访问需求，应先限定只含公开网页的服务目录并评估访问范围。

另一台电脑恢复时，可clone该仓库，从`fruit-fly/source/`取得全部源码和交接文件，复制到新的开发目录。相对路径不变；本文件中的旧绝对路径需按新环境确认。单文件线上页面是生成产物，优先从源码重建。
